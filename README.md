# Smart Home Telemetry

Проектная работа по курсу OTUS «Java Developer. Professional».

Система принимает поток показаний от датчиков умного дома, складывает их в PostgreSQL, считает агрегаты по временным окнам и шлёт оповещения по настраиваемым правилам.

Датчики ненастоящие, их эмулирует отдельный модуль. Зато проект не зависит от чужого железа и одинаково работает на любой машине.

## Как устроено

```
emulator  ──HTTP──►  gateway  ──RabbitMQ──►  processor  ──►  PostgreSQL
                        │                                        ▲
                        └────────── SSE / REST ◄─────────────────┘
                                        │
                                    браузер
```

Четыре модуля:

* common — модель, DTO, имена очередей, описание топологии RabbitMQ. Библиотека, приложением не является.
* emulator — крутит виртуальные датчики и шлёт их показания в gateway.
* gateway — принимает телеметрию, кладёт в очередь, отдаёт дашборд, историю и правила. WebFlux + R2DBC.
* processor — разгребает очередь, пишет в базу пачками, считает агрегаты, применяет правила, шлёт оповещения. Обычный Spring на виртуальных потоках.

Очередь между приёмом и обработкой стоит не для красоты. Она развязывает скорости (данные могут сыпаться быстрее, чем БД успевает писать) и позволяет пережить падение processor: сообщения полежат в RabbitMQ и дождутся.

### Почему в gateway реактивщина, а в processor нет

В gateway сплошной ввод-вывод: принять поток, сходить в базу, отдать поток. Ровно та ниша, ради которой WebFlux и придумали.

В processor всё наоборот. Клиент RabbitMQ блокирующий, отправка уведомлений блокирующая. Тащить туда Project Reactor значило бы обмазать каждый вызов subscribeOn(boundedElastic) и получить нечитаемые цепочки со стектрейсами на два экрана. Виртуальные потоки дают тот же выигрыш обычным кодом.

## Что нужно

JDK 25 и Docker Desktop. Остальное подтянет Gradle.

## Запуск

Поднять базу и очередь:

```
docker\up.cmd
```

Собрать:

```
gradlew build
```

Запустить приложения, каждое в своём окне:

```
gradlew :gateway:bootRun
gradlew :processor:bootRun
gradlew :emulator:bootRun
```

Порядок запуска не важен: топологию RabbitMQ объявляют оба сервиса из одного описания, а миграции накатывает gateway.

Дашборд: http://localhost:8090

Погасить инфраструктуру: docker\down.cmd. Данные останутся в томах.

## База

Пять таблиц: device (реестр датчиков), measurement (сырые показания), measurement_agg (агрегаты по окнам), alert_rule и alert_event.

Смысл разделения measurement и measurement_agg в следующем. Датчик шлёт показание раз в секунду, за сутки это под сотню тысяч строк на устройство, и хранить такое вечно бессмысленно. Сырые данные живут ограниченное время и удаляются, а свёрнутые в минутные и часовые окна остаются навсегда. График за месяц строится по агрегатам, график за последний час по сырым. Дашборд выбирает источник сам и пишет рядом с заголовком, откуда взял данные.

Свёртка идёт одним SQL-запросом с on conflict do update и перекрывает интервалы: каждую минуту пересчитываются окна за последние пять. Показание могло опоздать в очереди и попасть в уже посчитанное окно, поэтому задача сделана идемпотентной. Часовые окна считаются из минутных, а не из сырых данных, иначе после очистки пересчитать час стало бы невозможно. Среднее при этом берётся взвешенное: sum(avg_value * cnt) / sum(cnt).

## Правила и оповещения

Правила лежат в таблице alert_rule и добавляются прямо с дашборда. Processor перечитывает их раз в 15 секунд, перезапуск не нужен.

Условия: GT (больше верхнего порога), LT (меньше нижнего), OUT_OF_RANGE (вне диапазона), NO_DATA (датчик молчит).

От спама защищают две настройки. consecutive_count требует N нарушений подряд, поэтому одиночный выброс датчика игнорируется, а счётчик сбрасывается первым же нормальным значением. cooldown_seconds не даёт повторить оповещение по той же паре «правило и устройство», пока не истечёт пауза. Без этого при опросе раз в секунду духота в кухне давала бы 60 сообщений в минуту.

Каналы доставки сделаны через интерфейс NotificationChannel: сейчас LOG и WEBHOOK. Диспетчер собирает их в мапу по имени, получая List<NotificationChannel> в конструкторе, так что добавить телеграм означает написать новый класс и не трогать существующие. Результат доставки пишется в alert_event.delivered.

NO_DATA живёт отдельной задачей по расписанию: молчание по определению не приходит ни с каким показанием, поэтому проверяется поле device.last_seen_at.

## Тесты

```
gradlew test
```

Docker нужен: интеграционный тест поднимает свой PostgreSQL через Testcontainers.

* RuleEngineTest — условия, срабатывания подряд, сброс счётчика, фильтр по комнате и метрике. На моках, без базы.
* AlertNotifierTest — cooldown и его независимость по устройствам, поведение при неизвестном канале.
* SensorStateTest — 10 000 шагов случайного блуждания не выводят значение за физические пределы.
* LiveTelemetryStreamTest — StepVerifier: поток горячий, показание доходит до всех подписчиков.
* AggregationJobIntegrationTest — Testcontainers, настоящие миграции: свёртка считает min/max/avg/count, повторный запуск не плодит дубликаты, часовое окно берёт взвешенное среднее, очистка не трогает агрегаты.

Тест поймал реальную ошибку: Sinks.many().multicast().onBackpressureBuffer() придерживает элементы, пришедшие до первого подписчика, и отдаёт их ему при подписке. Открытый дашборд первым делом получал бы устаревшие показания. Заменено на directBestEffort.

Ради тестируемости загрузка правил уехала из RuleEngine в отдельный RuleRepository. Раньше движок сам держал JdbcTemplate и SQL, и проверить его без базы было невозможно.

## Нагрузка

Частота эмулятора задаётся на запуске, пересобирать ничего не надо:

```
gradlew :emulator:bootRun --args="--emulator.interval-millis=20"
```

Наблюдать удобно в админке RabbitMQ на вкладке Queues: видно скорость поступления и разбора, а также глубину очереди.

| интервал, мс | показаний в секунду | размер пачки | глубина очереди |
| --- | --- | --- | --- |
| 1000 | 16 | 30–110 | 0 |
| 100 | 160 | 500 | 0 |
| 20 | 800 | 500 | 0 |

На 800 показаниях в секунду очередь по-прежнему пуста, то есть предел найти не удалось: раньше упирается сам эмулятор. Узкое место системы лежит выше проверенного диапазона.

При интервале 1000 мс пачка закрывается по таймауту приёма и получается маленькой. При 100 мс сообщения идут сплошным потоком, пачка каждый раз добирает максимум в 500 и на одну транзакцию приходится 500 строк вместо полусотни. Настройки при этом не менялись: система подстроилась сама. Отсюда же видно, где искать резерв при дальнейшем росте нагрузки — увеличивать batch-size, а не добавлять потоки.

Проверка устойчивости: остановить processor на минуту при работающем эмуляторе. Счётчик сообщений в очереди растёт, дашборд продолжает рисовать живой график (он не зависит от записи в базу), после запуска processor очередь разбирается до нуля и в базе оказываются все показания.

## Грабли

**Flyway в реактивном приложении молчит.** Автоконфигурация Flyway включается, если в контексте есть бин DataSource либо задано свойство spring.flyway.url. В WebFlux-приложении с R2DBC никакого DataSource нет, так что без явного spring.flyway.url Flyway пропускают. Без ошибки, без предупреждения, вообще без единой строчки в логе: приложение стартует как обычно, просто база пустая. Полчаса ушло, пока догадался.

Ещё имена свойств у Flyway и DataSource разъезжаются: spring.datasource.username, но spring.flyway.user.

**Jackson 2 в Spring Boot 4 больше нет.** Боот перешёл на Jackson 3 (пакет tools.jackson), а старого com.fasterxml.jackson.databind в classpath не осталось. Половина примеров из интернета отваливается с ClassNotFoundException на JsonMapper. В Spring AMQP вместо Jackson2JsonMessageConverter теперь JacksonJsonMessageConverter, старый помечен deprecated и скоро уедет.

**Testcontainers выпал из управляемых зависимостей Boot 4.** Раньше версия подставлялась сама, теперь BOM подключается явной строкой.

**Модуль без плагина Spring Boot собирается без -parameters.** Имена параметров методов не попадают в байт-код, и Spring не может выбрать между двумя бинами одного типа. Флаг включён для всех модулей в корневом build.gradle.kts.

**Приложение без веб-сервера завершается сразу.** Потоки планировщика Reactor демонские, main закончился и JVM вышла, не дав Flux.interval ни одного тика. Лечится настройкой spring.main.keep-alive.

**Очередь должны объявлять оба сервиса.** Сначала топология была только в gateway, и processor падал с NOT_FOUND, если gateway не поднялся. Описание переехало в common и подключается через @Import. Объявление идемпотентно, но только при полностью совпадающих параметрах: объяви processor ту же очередь без dead-letter, RabbitMQ ответил бы PRECONDITION_FAILED. Поэтому описание одно на всех, а не скопировано в два места.

## Состояние

Сделано всё запланированное: инфраструктура и схема БД, сквозной поток данных, дашборд с живым графиком, агрегация по окнам с очисткой сырья, правила и оповещения, тесты, замеры под нагрузкой.

Чего осознанно нет: аутентификации, кластеризации, MQTT вместо HTTP на приёме телеметрии, вытеснения старых агрегатов. Для учебного проекта это лишний объём, а архитектура их добавление не блокирует.
